# 参数外显与判断外显：评审的两条姊妹机制

## 使用阶段限定（2026-04-21 补）

==本机制专用于"代码实现后的反馈迭代阶段"==——和 [[审美是隐性认知，追问是唯一的解压工具]] 同域，都服务代码生成后的用户反馈闭环。代码实现前的"目标 / 架构 / 文案"边界建立走 [[深度采访双轮：产品设计师视角的横切机制]]，不走本机制。

## 一句话

==AI 前端评审有两条独立的外显化通路==：**判断外显**（把用户说不清的审美感觉翻译成可讨论的选项）和**参数外显**（把不必一次决策的参数做成可实时调的旋钮）。前者解决"用户说不清"，后者解决"用户不想现在决定"。

两者都是把隐性变显性，但**隐性的来源不同**——前者是认知隐性（用户自己也不清楚），后者是决策隐性（用户暂时懒得判断）。

## 两条通路对照

| 维度 | 判断外显 | 参数外显 |
|---|---|---|
| **隐性发生在哪** | 用户的审美系统（感到不对但说不出) | 用户的决策负担（可以判断但懒得一次定死） |
| **机制名** | 三段式追问（定位 → 对标 → 量化） | Tweaks 面板 / Design Canvas / 可切换选项 |
| **Agent 动作** | 提出 2-3 个具体选项让用户选 | 暴露 N 个可调参数让用户摸 |
| **用户动作** | 选（离散） | 调（连续 or 枚举） |
| **上游笔记** | [[审美是隐性认知，追问是唯一的解压工具]] | 本笔记 |
| **适用时刻** | 评审时"感觉不对" | 方向不确定、变体之间摇摆、中间态想看多个组合 |

## 为什么参数外显是独立机制

过去我把所有评审问题都推给三段式追问——本质上每次都在逼用户"做一次决定"。但有些问题的正确答案不是"选 A 还是选 B"，而是"让我看到连续滑动过 A 到 B 的过程再说"。

这种时候做参数外显比做选择题更贴合隐性发生的位置：用户不是判断不出来，而是==在没看到连续对比前根本无法形成判断==。强行让他选就是让他瞎选。

Anthropic Design 系统提示词里的 Tweaks 协议本质就是这个理念：

- 用户的决策可以延迟到"看到实时变化再说"
- 参数默认嵌在成品里，关了 tweaks 就是定稿
- 哪怕用户没要求 tweaks，也默认给几个——==让用户发现他本来没想到可以调的维度==

## 如何判断该用哪条

遇到评审问题时先做一次分类：

| 症状 | 走哪条 |
|---|---|
| 用户说"就是感觉不对" | **判断外显**——三段式追问 |
| 用户说"可能 A 可能 B，不确定" | **参数外显**——暴露成 tweak 让他切换 |
| 用户说"能不能更 X 一点" | **参数外显**——把 X 做成滑块或枚举 |
| 用户说"其他地方都好就是这个 section" | **判断外显**——定位 + 对标这一段 |
| 用户沉默、不置可否 | **参数外显**——主动暴露 2-3 个他没提的维度，让他摸着发现偏好 |
| 用户的反馈互相矛盾 | **判断外显**——逼出底层取舍：你要清晰还是要惊喜 |

==判断外显偏"收敛"，参数外显偏"发散"==。评审早期散，评审后期收。

## 参数外显的落地规则

借鉴自 Anthropic Design Tweaks 协议，抽象到方法论层：

### 1. 可调范围要慷慨

用户常常想走得比你预期更远。除非物理受限（opacity 0-1、饱和度 0-100），否则别把滑块范围卡得太紧。

### 2. 默认态 = 定稿态

Tweaks 关闭时页面应该看起来像最终版，**不是调试界面**。这让用户可以随时说"就这样了"，不用再做"清理 debug UI"的额外动作。

### 3. 暴露用户没想到的维度

用户只说了"颜色可能不对"时，除了颜色滑块外，==再默认加一两个他没提到的参数==（比如字距、圆角、阴影强度）。用户往往会意外发现这些维度也有感觉。

### 4. 参数要覆盖决策空间两端

给一个 primaryColor 滑块时，默认值不要停在中间——要让滑到最左/最右都产生肉眼可辨的视觉差。否则用户调不出差别就放弃了。

### 5. 变体枚举 vs 连续参数

- 连续参数：字号、字距、间距、圆角、饱和度、阴影强度
- 枚举参数：字体家族、layout 变体、icon pack、配色主题
- 混合时先枚举后连续——先选大方向再微调

### 6. 持久化到磁盘

Agent 侧：tweak 值变化时要能写回源文件，刷新不丢。这是 Anthropic 的 `/*EDITMODE-BEGIN*/`/`/*EDITMODE-END*/` 标记机制做的事——方法论上叫"决策固化"：当用户把参数摸到满意位置，那个状态就是新的默认，不是临时覆盖。

## 和七层框架的关系

参数外显是**层 5 评审层的补丁机制**：

```
[层 5] 评审
  ├─ 判断外显通路：用户"感觉不对" → 三段式追问 → 离散选择
  └─ 参数外显通路：用户"不确定 / 想看对比" → Tweaks / Canvas → 连续调节
     ↓
  两条通路都通往：把隐性变显性
     ↓
  反写回 [层 3] DESIGN.md（唯一记忆通路）
```

不新增一层，只在层 5 里并联一条路由。

## 三段式追问 + 参数外显的配合

实战里两者经常嵌套使用：

1. 用户说"不对" → 判断外显：Agent 追问"哪里不对"
2. 用户定位到某个 section → 判断外显：给 2-3 个方向选项
3. 用户选了"方向 B" → ==切换到参数外显==：把方向 B 里的字号/间距/密度做成 tweak 让用户摸
4. 用户摸到满意值 → 固化为新 DESIGN.md 的 §2-§5 token
5. 回到其他 section，回到判断外显

两条通路是同一次评审会话的两个档位，不是二选一。

## 反例：什么情况下不要用参数外显

- **方向错了还暴露参数**——用户说"整个配色都不对"时，给他 N 个颜色滑块只会让他在错方向里挣扎。先用判断外显换方向
- **无意义的参数**——某个 tweak 值跨整个范围都看不出差别，说明这个参数不是真变量，删掉
- **把工程 debug 塞给用户**——`console.log` 开关、性能计时器这类不属于设计参数，不该放进 tweak 面板
- **参数超过 6 个**——超过就是把决策压力转移到用户身上，应该先做判断外显收敛主方向
