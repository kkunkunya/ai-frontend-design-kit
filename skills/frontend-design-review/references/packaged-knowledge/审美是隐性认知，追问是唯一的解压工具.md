# 审美是隐性认知，追问是唯一的解压工具

## 使用阶段限定（2026-04-21 补）

==本机制专用于"代码实现后的反馈迭代阶段"==——用户看到具体页面后涌现"感觉不对"时启动三段式追问。

与之正交的是 [[深度采访双轮：产品设计师视角的横切机制]]，后者服务"代码实现前的目标建立阶段"。两者关系：

| 机制 | 阶段 | 目的 |
|---|---|---|
| **深度采访双轮** | 代码之前 | 建立目标 / 架构 / 文案的边界 |
| **审美追问三段式**（本笔记） | 代码之后 | 纠正"感觉不对"的评审反馈 |

==不要混用==：前置阶段用审美追问，用户答不出具体反馈（没看到实物）；后置阶段用深度采访，会问已经答过的定位问题。

## 一句话

==审美判断本质是隐性认知==——用户自己也说不清，但他一看到就知道对不对。AI 要求用户一次性把所有审美标准讲清楚，是在要求一件物理上不可能的事。==解压这份隐性认知的唯一工具是追问==，不是 prompt、不是 skill、不是更好的设计系统。

## 为什么审美是隐性认知

隐性知识（tacit knowledge，Polanyi）的核心特征：**知道得比能说出来的多**。审美属于这类：

- 用户能立刻判断"这个高级 / 那个掉线"
- 但他无法一次写出"高级的判断标准"清单
- 他的判断来自==累积的参考样本比对==，样本本身藏在他的视觉记忆里
- 他看 Dragonfly 一眼就知道"这是我想要的气质"，但无法描述"这是哪种气质"

这不是用户的问题，是认知机制本身的问题。所有真正的审美判断（书法、音乐、建筑、平面设计）都有这个特点。==不要期望它能被显式传递==。

## 两个错误的工作模式

### 错误 1：让用户先写"审美标准"再开工

典型对话：

> AI：请描述你对这个页面的审美期望
> 用户：高级、干净、有设计感、不要俗套
> AI：✓ 开始生成
> 结果：生成的东西全部是俗套

为什么失败：==用户给出的是二阶描述（抽象词汇），AI 需要的是一阶描述（具体参数）==。两者之间的翻译必须在有具体参考物的时候做，不能凭空做。

### 错误 2：让用户一次性指出所有问题

典型对话：

> AI：[生成第一版]
> 用户：不对
> AI：哪里不对？
> 用户：整体感觉不对，就是不高级
> AI：可以具体说吗？
> 用户：就是差点意思
> [AI 再改 10 次，每次都不对]

为什么失败：==用户的"感觉不对"是整体判断，是隐性认知的自然输出形式==。强求他把这个整体判断拆成一组显性条目，等于让他做一件大脑不是这样工作的事。

## 正确工作模式：AI 主动追问

正确的解压流程==反过来==：用户负责给"感觉"（非结构化反馈），AI 负责==一层一层地问==，逐步把这份感觉从整体判断变成可执行的改动项。

### 分工重新定义

| 角色 | 负责 | 不负责 |
|---|---|---|
| **用户** | 感觉判断（"哪里不对"、"这个好"、"那个糟"） | 说清楚为什么、提供参数、写标准 |
| **AI** | 把感觉追问成具体维度 + 参数 + 可执行改动 | 自己判断什么好看 |

这个分工==完全颠倒了常见的"用户提需求 AI 执行"模式==。审美场景下，用户只提"这样 / 不这样"的判断信号，AI 负责把信号翻译成可执行。

### 追问的三段式

从一个"不对"到一个可执行改动，至少要走三步追问：

#### 第一步：定位（Where）

```
✓ 好的追问：
- "是整体不对还是某个 section 不对？"
- "你视线第一眼落在哪里？那个地方对不对？"
- "最不对的地方能框一下吗？（让用户截图 + 圈）"

✗ 糟糕的追问：
- "具体哪里不对？"（太开放）
- "是字体问题吗？"（窄化，可能漏掉真实原因）
```

#### 第二步：对标（Against What）

```
✓ 好的追问：
- "和参考站的哪个地方对比起来不对？"
- "你心里理想的它应该像什么？能指个具体例子吗？"
- "你觉得它更像 A 还是 B？"（给出两个具体参考）

✗ 糟糕的追问：
- "你希望它是什么风格？"（要求用户生成二阶描述）
- "能形容一下吗？"（要求用户组织语言描述视觉）
```

#### 第三步：量化（How Much）

```
✓ 好的追问：
- "字号要大 2 档还是 3 档？（我举个例子：26 → 34 还是 26 → 40）"
- "这段文字感觉应该占屏幕左右多少？大约一半还是三分之二？"
- "这个动效的触发时机，应该比现在早一点还是晚一点？"

✗ 糟糕的追问：
- "字号应该是多少？"（用户不是设计师，给不出像素数）
- "你觉得合适的比例是？"（抽象）
```

关键原则：==第三步的追问必须给用户具体选项==，让他做选择题而不是填空题。

### 追问的"选择题化"模式

当用户说"布局太松散"时：

```
AI：我先量了下当前布局，发现：
- 容器宽 896px（视口 1728 的 52%）
- 段落总高 1359px
- 段间距 112px

你觉得应该：
A) 容器收紧到 768px，段间距减到 56px（收紧约 30%）
B) 容器保持，只减段间距到 56px（只收竖向）
C) 容器收到 640px，段间距减到 40px（大幅收紧）

你更接近哪个？
```

这样用户只需要做 A/B/C 选择，不需要自己算参数。AI 承担了==把隐性感受翻译成具体选项==的工作。

## 高级感不是单一维度

本轮最大的一个误会：早期我以为"高级感 = 左右不要空"。用户反驳：==留白可以很美==，关键是"从具体网页里把高级感量化出来"。

### 高级感的真实维度（需要从参考站逐项量化）

- **字体选择**：Serif + Mono 混搭？字重 300 light？letter-spacing 0.04em？
- **行高节奏**：1.1 还是 1.35？
- **颜色对比度**：#F2F2F2 on #000 vs #CCC on #141414
- **间距比例**：横向间距 / 竖向间距 = 黄金比？1:1.618？
- **留白使用**：留白要有目的性（停顿 / 分段 / 强调），而不是被迫的空
- **层级差异**：主次字号比例 1.5x? 2x?
- **动效节奏**：快 UI 过渡 0.35s，慢转场 0.8s
- **异常细节**：品牌字母散在四角的 opacity 0.5 衬线
- **无 AI 味**：文案不像 prompt 输出，标签大写 mono，图标像素风

==这些每一项都要从参考站具体量化出来才能复现==。随便哪一项没量化，就会失真。详见 [[从参考案例复刻高级感：量化工作流]]。

### 空 vs 有内容：不是对立关系

| 空是好的 | 空是坏的 |
|---|---|
| 有明确意图（主视觉单点爆破） | 只是懒得填 |
| 带节奏（停顿 → 主体 → 停顿） | 全局均匀稀疏 |
| 和主语言一致（极简派） | 和主语言冲突（应该密集却稀疏） |
| 有数学关系（8倍栅格留白） | 随机大小 |

判断空是否合理的唯一方法：==和参考站对位比较==。单独看当前页说"空"没有意义。

## FORGE 案例：从定性到量化的完整链

### 链条示范：用户说 "两边太空了"

**第一步：定位（AI 追问）**

> "是 Hero 太空还是 WhatWeDo 太空？你指的是水平方向（左右）还是整体都空？"

用户：WhatWeDo。水平，左右。

**第二步：对标**

> "是对比 Dragonfly 的 ABOUT 段吗？那段文字是顶到视口两边的"

用户：对，应该那样。

**第三步：量化**

AI 用浏览器插件打开 Dragonfly ABOUT 截图，测量 / 推算：

- 段落 1：左边缘 viewport 5%，右边缘 ~55%
- 段落 2：左边缘 viewport 22%，右边缘 ~95%
- 两段水平重叠区：22% ~ 55%
- 字号：~32-36px serif body
- 段间垂直间距：很小（像连续正文）

AI 给出 FORGE 改动方案：

```
Para1：md:w-[55%]，左对齐（从 section padding 起）
Para2：md:ml-auto md:w-[60%]，text-right（右对齐到 section padding）
字号：Para1 44-68px，Para2 30-46px（响应式）
段间距：mt-4 ~ mt-6
```

用户：改了以后好多了，但 "CONNECT 比其他两个暗"。

**再追问第二轮**——定位 → 发现是 staggered scroll ranges → 合并共享 motion value → 解决。

这就是一次完整的==隐性认知 → 显性改动==的解压过程。==每一步都是追问，每一步都给具体选项==。

## 追问的节奏：不要一次问太多

一次追问最多 3 个问题，最好 1 个。问太多用户会选择性回答，隐性认知反而被遮蔽。

**节奏模式**：

```
1. 问一个定位问题
2. 等用户回答
3. 基于回答问一个对标问题
4. 等用户回答
5. 基于回答给 2-3 个量化选项
6. 用户选一个
7. AI 执行
8. 用户看结果，给新的定性反馈
9. GOTO 1
```

每轮==都在把用户的隐性判断往显性推一点==。不要跳步。跳步会回到"让用户一次说清"的错误模式。

## 工具：DOM 是追问的证据基础

追问需要证据，证据来自参考站和当前实现的 DOM 对比：

```javascript
// 通用 DOM 审美测量脚本
(() => {
  const target = document.querySelector('...');
  const cs = getComputedStyle(target);
  const rect = target.getBoundingClientRect();
  return {
    位置: { top: rect.top, left: rect.left, w: rect.width, h: rect.height },
    字体: { family: cs.fontFamily, size: cs.fontSize, weight: cs.fontWeight,
           leading: cs.lineHeight, tracking: cs.letterSpacing },
    颜色: { fg: cs.color, bg: cs.backgroundColor },
    间距: { m: cs.margin, p: cs.padding },
    相对视口: `${Math.round(rect.width / window.innerWidth * 100)}%`,
  };
})();
```

拿着这份数据去追问：

> "参考站的这段文字是 44px serif light，占视口 52%。你当前的是 26px grotesk light，占 32%。你觉得是字号不够还是宽度不够？"

==量化是 AI 的活，感觉是用户的活==。有了量化数据，追问才能精准。

## 要抵抗的诱惑

- ❌ "让用户先写清楚审美标准再开工" → 他写不出来
- ❌ "用户说不清就凭自己经验做决定" → 你的经验是错的那部分恰好是隐性认知
- ❌ "我看过很多网站我知道什么好看" → 具体判断必须发生在具体上下文里
- ❌ "追问太多用户会烦" → 比让用户一次说清清更好；用户烦是因为追问方式不对（问得太抽象 / 一次问太多）
- ❌ "这一轮先这样，下一轮再说" → 隐性认知会快速遗忘，下一轮就是新的隐性状态
